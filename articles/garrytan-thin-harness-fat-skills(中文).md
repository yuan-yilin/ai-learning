Steve Yegge 说,使用 AI 编码 agent 的人"生产力是用 Cursor 和聊天的工程师的 10 到 100 倍,大约相当于 2005 年 Google 工程师的 1000 倍。"

这是一个真实数字。我见过,我也亲身经历过。但当人们听到这句话时,他们总是找错解释——更好的模型、更聪明的 Claude、更多参数。但 2 倍生产力和 100 倍生产力的人用的是同一批模型。差异不在智能,而在架构——一张索引卡就能写完。

## 产品就是 harness

2026 年 3 月 31 日,Anthropic 意外把 Claude Code 的全部源代码发布到了 npm 上。51.2 万行。我读了一遍。它印证了我在 YC 一直讲的东西:秘密不在模型,而在包裹模型的那层东西。

实时仓库上下文。提示词缓存。专用工具。上下文膨胀最小化。结构化会话记忆。并行子 agent。这些没有一项让模型更聪明,全部只是在合适的时机给模型合适的上下文,不让它淹没在噪声里。

那层包裹就叫 harness。每个 AI 构建者都该问一个问题:什么进 harness,什么留在外面?答案有一个具体的形状,我称之为**瘦 harness、胖 skills**。

## 五个定义

瓶颈从不是模型的智能。模型早就知道如何推理、综合、写代码。它们失败是因为不理解你的数据——你的 schema、你的约定、你问题的特定形状。五个定义能解决这件事。

**1. Skill 文件**

Skill 文件是一份可复用的 markdown 文档,教模型如何做某件事。不是做什么——那是用户提供的。Skill 提供的是过程。

多数人忽略的关键洞察是:**skill 文件就像一次方法调用。** 它接受参数,你可以用不同参数调用它。同一个流程,传入不同实参,会产出截然不同的能力。

考虑一个叫 /investigate 的 skill。它有七步:界定数据集、建立时间线、为每份文档做日志化、综合、正反两方论证、引用来源。它接受三个参数:TARGET、QUESTION 和 DATASET。把它指向一位安全科学家和 210 万封取证邮件,你就得到一位医学研究分析师,判断一位吹哨人是否被噤声。把它指向一家空壳公司和 FEC 备案文件,你就得到一位法务调查员,追踪协调的政治献金。

同一个 skill,同样的七步,同一份 markdown 文件。skill 描述的是一套判断流程,调用提供的是世界本身。

这不是提示词工程。这是软件设计,以 markdown 作为编程语言、以人类判断作为运行时。事实上,markdown 是比刚性源代码更完美的能力封装,因为它用模型本就用来思考的语言来描述流程、判断和上下文。

**2. Harness**

Harness 是运行 LLM 的那个程序。它做四件事:在循环中跑模型、读写你的文件、管理上下文、执行安全约束。就这些。这就是"瘦"。

反模式是胖 harness 配瘦 skills。你应该见过:40+ 个工具定义吃掉一半上下文窗口。带 2 到 5 秒 MCP 往返的"上帝工具"。把每个 REST 端点都包成单独工具的 API 封装。三倍的 token、三倍的延迟、三倍的失败率。

你真正要的是专用、快速、窄的工具。一个 Playwright CLI 每个浏览器操作 100 毫秒完成,而不是一个 Chrome MCP 截图-查找-点击-等待-读取要 15 秒。快了 75 倍。软件不必再那么精贵,只造你正好需要的,别的不多造。

**3. Resolver**

Resolver 是一张上下文路由表。当任务类型 X 出现时,先加载文档 Y。

Skills 告诉模型怎么做。Resolver 告诉它加载什么、何时加载。一个开发者改了提示词。没有 resolver,他直接发布。有 resolver,模型会先读 docs/EVALS.md——上面写着:跑评测套件、对比分数、若准确率下降超过 2% 就回滚并调查。开发者原本不知道评测套件的存在,resolver 在合适的时机加载了正确的上下文。

Claude Code 内置了一个 resolver。每个 skill 都有一个 description 字段,模型会自动把用户意图匹配到 skill 描述上。你永远不必记住 /ship 存在,描述本身就是 resolver。

坦白一句:我的 CLAUDE.md 曾经有 2 万行。每一条癖好、每一个模式、我遇到过的每一个教训。完全荒唐。模型的注意力明显退化。Claude Code 直接叫我砍掉。修复后大约 200 行——只是指向文档的指针。resolver 在需要时加载正确的那份。两万行知识按需可取,不污染上下文窗口。

**4. 潜在 vs 确定**

你系统里的每一步,非此即彼,而混淆两者是 agent 设计中最常见的错误。

**潜在空间(laten)** 是智能所在。模型读、解读、决策。判断、综合、模式识别。

**确定(deterministic)** 是信任所在。同输入、同输出,每次都一样。SQL 查询、编译后的代码、算术。

一个 LLM 能安排 8 人的晚宴座次,兼顾性格和社交动态。让它排 800 人,它会凭空造出一张看起来合理、实则全错的座次表。那是确定性问题——组合优化——却被硬塞进了潜在空间。最差的系统把错误的活放到了这条线错误的一侧。最好的系统对此极其严苛。

**5. 日志化(Diarization)**

日志化是让 AI 真正可用于知识工作的那一步。模型读尽某主题的全部材料,写一份结构化画像——一页纸的判断,从几十上百份文档中蒸馏出来。

没有任何 SQL 查询能产出它。没有 RAG 管线能产出它。模型必须真正去读、在脑中同时容纳矛盾、注意什么在何时发生了变化,并综合成结构化的情报。这是数据库查询和分析师简报之间的差别。

## 架构

这五个概念组合成一个简洁的三层架构。

**胖 skills** 在顶层:编码判断、流程和领域知识的 markdown 流程。90% 的价值在这里。

**瘦 CLI harness** 在中层:大约 200 行代码。JSON 进、文本出,默认只读。

**你的应用** 在底层:QueryDB、ReadDoc、Search、Timeline——确定性的地基。

这个原则是方向性的:把智能上推到 skills,把执行下压到确定性工具,让 harness 保持瘦。这样做了之后,模型的每一次提升都会自动惠及每一个 skill,而确定性层始终完全可靠。

## 会学习的系统

让我把五个定义放在一起展示。不是理论,而是我们在 YC 正在搭的一个真实系统。

大通中心。2026 年 7 月。六千位创始人在 Startup School。每人有一份结构化申请、问卷答案、1:1 顾问聊天的记录,以及公开信号:X 上的帖子、GitHub 提交、展示他们出货速度的 Claude Code 记录。

传统做法:一个 15 人的 program 团队读申请、凭直觉拍板、更新一张表格。200 位创始人时行得通,6000 位时就崩了。没有任何人能在工作记忆里装下那么多画像,并注意到:AI-for-agents 基础设施 cohort 最合适的三位候选人,是一位拉各斯的开发工具创始人、一位新加坡的合规创始人、一位布鲁克林的 CLI 工具创始人——这三人在 1:1 聊天中用不同措辞描述了同一个痛点。

模型可以。做法如下。

**丰富化。** 一个叫 /enrich-founder 的 skill 拉取所有来源、跑增补、做日志化,并标出创始人"说的"和他们"真正在做的"之间的落差。确定性层处理 SQL 查询、GitHub 统计、demo URL 上的浏览器测试、社交信号抓取、CrustData 查询。一个 cron 每晚跑一次。六千份画像,始终新鲜。

日志化的输出能抓住任何关键词搜索都抓不到的东西:

FOUNDER: Maria Santos  COMPANY: Contrail (contrail.dev)  SAYS: "Datadog for AI agents"  ACTUALLY BUILDING: 80% 的提交在计费模块。她在做一个披着可观测性外衣的 FinOps 工具。

这条落差——"说的"对"真正在做的"——需要读 GitHub 提交历史、申请表和顾问记录,并同时把三份都放在脑中。没有任何 embedding 相似度搜索能找到它。没有关键词过滤器能找到它。模型必须读完整画像并做出判断。(这正是最适合放进潜在空间的决策!)

**匹配。** 这正是"skill 即方法调用"大放异彩之处。同一个匹配 skill 的三次调用,三种完全不同的策略:

/match-breakout 取 1200 位创始人,按行业亲和力聚类,每间 30 人。Embedding 加确定性分配。/match-lunch 取 600 位,跨行业做机缘匹配,每桌 8 人,不重复——LLM 来发明主题,再用确定性算法排座。/match-live 处理此刻在楼里的人,最近邻 embedding,200 毫秒,1:1 配对,排除已经见过面的人。

而模型能做出聚类算法永远做不出的判断:"Santos 和 Oram 都是 AI 基础设施,但他们不是竞品——Santos 做成本归因,Oram 做编排。把他们放一组。"或者:"Kim 以'开发工具'申请,但他 1:1 记录显示他在做 SOC2 的合规自动化。把他挪到 FinTech/RegTech。"

没有任何 embedding 能抓住对 Kim 的重新分类。模型必须读完整画像。

**学习闭环。** 活动结束后,一个 /improve skill 读 NPS 调研、对"还行"的回答做日志化——不是差的那批,是"还行"的那批,系统差点跑通但没跑通的地方——并提取模式。然后它提出新规则,写回到匹配 skills 里:

当 attendee 说"AI infrastructure"但 startup 80%+ 是计费代码:→ 归类为 FinTech,而非 AI Infra。当同组两位 attendee 已经互相认识:→ 惩罚邻近度,优先安排新结识。

这些规则被写回到 skill 文件里。下次运行自动用上。skill 重写了自己。

7 月那场:12%"还行"评级。下一场:4%。skill 文件学到了"还行"到底是什么意思,系统在没人改代码的情况下变好了。

同一个模式可迁移到任何地方:检索、阅读、日志化、计数、综合。然后:调研、调查、日志化、重写 skill。

如果你想知知道 2026 年最有价值的闭环是什么,就是这些。我们能把它应用到知识工作的每一个学科和每一种生活方式上。

## Skills 是永久升级

我最近发了一条给 OpenClaw 的指令,反响超出预期:

你不得做一次性工作。如果我让你做一件事,而它是那种以后还会再发生的事,你必须:第一次先手动对 3 到 10 个条目做一遍。给我看输出。我批准后,把它固化成一个 skill 文件。如果它该自动跑,就挂到 cron 上。测试标准:如果我得第二次向你要同一件事,你就失败了。

一千个赞、两千五百个收藏。人们以为这是个提示词工程技巧。不是。它就是我一直在描述的架构。你写的每一个 skill 都是对你系统的一次永久升级。它永不退化,永不遗忘,凌晨 3 点你睡觉时它照跑。当下一个模型发布时,每个 skill 瞬间变好——潜在步骤里的判断力提升,而确定性步骤依旧完全可靠。

这就是你拿到 Yegge 说的 100 倍的方法。不是更聪明的模型。胖 skills、瘦 harness,以及把一切固化下来的自律。

系统会复利增长。搭一次,跑永远。
